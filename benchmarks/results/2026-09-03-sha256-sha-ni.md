# SHA-256 with Intel SHA Extensions (2026-09-03)

Second optimization of the day, on the same machine and toolchain as the
baseline file (2026-09-03-amd-epyc-9k65-shared-cloud.md): shared cloud
container, AMD EPYC 9K65, rustc 1.98.0 / LLVM 22.1.8, estimated 3690 MHz,
baseline x86_64 target features, so acceleration comes from runtime dispatch.

Selected backend: x86_64-sha-ni (reported by cargo run --release --bin bench-env).

## What changed

* crates/fastcrypto-x86/src/sha256.rs: SHA-256 compression with
  sha256msg1/sha256msg2/sha256rnds2, gated on the cached CPUID probe and
  falling back to the portable path when SHA-NI is absent.
* crates/fastcrypto-core: gained a safe dispatch seam. Compressor is a plain
  function pointer, carried by Sha256, HmacSha256 and HkdfSha256, so the
  backend is chosen once per instance and no dispatch happens per block.
* crates/fastcrypto: the public types now select the best backend at
  construction. The one unsafe block lives in fastcrypto-x86 behind the
  runtime feature check; the public crate stays forbid(unsafe_code).

## Correctness

* crates/fastcrypto-bench/tests/backend_equivalence.rs: SHA-NI and portable
  agree for every length in 0..600, at the padding boundaries (55/56/57,
  63/64/65, 119/120/127/128/129, 191/192/193), under 16 different chunkings
  of a 5000-byte message, and for 64 KiB and 100 kB inputs.
* tests/differential.rs now runs through the accelerated path and still
  matches RustCrypto, ring and aws-lc-rs.
* FIPS 180-4 KAT vectors pass directly against the SHA-NI compression
  function (fastcrypto-x86 unit tests).

## Analysis

### Large inputs: level with the established libraries, not ahead of them

At 64 KiB we measure 36.10 us against ring 35.93 us and aws-lc-rs 35.86 us: a
difference of 0.5-0.7%, which is inside the noise of a shared container. The
honest statement is that our SHA-256 is now indistinguishable from both of them
at 1 KiB and above in this run. It is not faster, and this machine cannot
resolve the difference; confirming it needs a dedicated machine with a fixed
clock, which is the rule this project set for itself before making claims.

### Small inputs: still behind, and the reason is fixed cost

| size | fastcrypto | aws-lc-rs | gap |
|---|---|---|---|
| 0 B | 97.5 ns | 61.6 ns | +58% |
| 64 B | 134.9 ns | 77.8 ns | +73% |
| 256 B | 242.8 ns | 180.8 ns | +34% |
| 1 KiB | 660.4 ns | 606.0 ns | +9% |

Construction alone is 26.9 ns for us and 2.5 ns for RustCrypto: Sha256 zeroizes
on drop (9 words plus a 64-byte block, volatile writes) and finalize zeroizes a
128-byte padding scratch. Those costs were a small fraction of a portable hash;
now that the hash itself is 5x faster they dominate everything below 256 bytes,
which is exactly the range TLS handshake hashing lives in.

### HKDF-SHA256 is now the weakest link

Extract + expand to 88 bytes (one TLS 1.3 traffic secret derivation) costs
1369 ns for us against 648 ns for RustCrypto hkdf, 819 ns for aws-lc-rs and
831 ns for ring. Two structural causes, both fixable:

1. Every HMAC in the expand chain rebuilds its ipad/opad key states (two extra
   compressions per HMAC). A TLS key schedule expands several labels from one
   PRK, so that work is repeated where it should be prepared once.
2. Every finalize zeroizes a 128-byte scratch buffer with volatile writes. With
   SHA-NI a compression is about 40 ns, so the zeroization is no longer noise.

Both are Milestone 3 work, and both are measurable in the existing harness.

### Conclusion for this change

Keep. SHA-256 improved 62-81% at every size, the accelerated path is proven
equivalent to the portable one by differential tests, and the remaining gaps are
now fixed-cost and dataflow problems rather than a missing instruction path.
No claim of beating ring or aws-lc-rs is made: at large sizes the numbers are
within noise, and at small sizes we are behind.
